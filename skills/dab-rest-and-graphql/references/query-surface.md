## Endpoint shapes

| Operation | Request |
|---|---|
| Read a collection | `GET /api/{entity}` |
| Read one row by key | `GET /api/{entity}/{key-column}/{key-value}` |
| Create | `POST /api/{entity}` |
| Replace | `PUT /api/{entity}/{key-column}/{key-value}` |
| Update | `PATCH /api/{entity}/{key-column}/{key-value}` |
| Delete | `DELETE /api/{entity}/{key-column}/{key-value}` |

The `/api` prefix is `runtime.rest.path` and the per-entity segment is `entities.<name>.rest.path`.
At 2.0 an entity path may contain forward slashes, so `"path": "shopping-cart/item"` produces
`/api/shopping-cart/item`. Routing is longest-prefix, and traversal sequences are rejected.

## REST query keywords

| Keyword | Purpose | Example |
|---|---|---|
| `$select` | Choose the fields returned | `?$select=id,title` |
| `$filter` | Restrict rows | `?$filter=year ge 1970 or title eq 'Dune'` |
| `$orderby` | Sort | `?$orderby=year desc, title asc` |
| `$first` | Page size | `?$first=5` |
| `$after` | Continue from the previous page | `?$first=5&$after={token}` |

`$filter` takes OData predicates: `eq`, `ne`, `gt`, `ge`, `lt`, `le`, `and`, `or`. A `$select`
naming a field that does not exist or is not permitted for the caller's role returns
`400 Bad Request`, which is how a field-level `exclude` shows up at the API.

`$first=-1` asks for the configured maximum page size.

## The response shape, and the empty-result trap

A successful read returns a `value` array, plus `nextLink` when more pages exist:

```json
{
  "value": [ { "id": 1, "title": "Dune" } ],
  "nextLink": "https://<host>/api/book?$after=<token>"
}
```

**A `GET` for a primary key that does not exist returns `200 OK` with an empty `value` array, not
`404 Not Found`.** Client code that branches on the status code reports a missing row as a
success. Branch on the array being empty.

Errors come back as an `error` object with `code`, `message` and `status`.

## Writes, and where PUT and PATCH surprise you

`PUT` and `PATCH` upsert: they update the row if it exists and create it if it does not. That only
works where the database accepts an explicit primary key value. **Against a table with an
`IDENTITY` key, a `PUT` or `PATCH` to a key that does not exist returns `404 Not Found`**, because
the database will not accept the explicit insert. Use `POST` to create rows on such a table.

Version 2.0 adds the keyless form: when every omitted key column is autogenerated, `PUT /api/Book`
with no key segment creates the row and the database assigns the key. For a composite key, any
portion that is not autogenerated must still appear in the URL.

By default the request body is strict: fields that are not columns, or that belong in the URL, are
rejected. `runtime.rest.request-body-strict` set to `false` relaxes this, which is what lets a
single client type serve both create and update.

## Stored procedures and views as entities

A stored procedure entity carries `source.type` of `stored-procedure` and takes `execute` as its
only action; `*` expands to `execute` alone. At 2.0 its parameters are an array of objects with
`name`, `required`, `default` and `description`, and the older dictionary form is deprecated.
`entities.<name>.rest.methods` controls which HTTP methods reach it, and it defaults to `POST`.

A view needs its key columns marked, through `fields[].primary-key`. Stored procedures are
excluded from entity health checks automatically, because they need parameters and need not be
deterministic.

## GraphQL

One endpoint at `runtime.graphql.path`, default `/graphql`. Each entity contributes a query named
from `graphql.type`, with `singular` and `plural` forms, and mutations named from the same type.
Relationships defined in the configuration become navigable fields, so a `Category` with a
`many` relationship to `Book` exposes `books` on the `Category` type. Without a relationship block
there is no navigation, whatever the foreign keys say.

`runtime.graphql.allow-introspection` is `true` in a configuration written by `dab init`. Turn it
off for a public deployment unless the schema is meant to be discoverable.
`runtime.graphql.depth-limit` bounds nested query depth, which is the defence against a deeply
nested query being used as an amplification attack.

## Runtime keys worth setting

| Key | Default | Why it matters |
|---|---|---|
| `runtime.pagination.default-page-size` | `100` | Every unbounded read is capped here |
| `runtime.pagination.max-page-size` | `100000` | The ceiling a caller can ask for |
| `runtime.cache.enabled` | off | Per-entity `cache.enabled`, `cache.ttl-seconds` and `cache.level` layer on top |
| `runtime.compression.level` | none | `optimal`, `fastest` or `none`, added at 2.0 |
| `runtime.host.mode` | `production` | `development` relaxes error detail and exposes more of the surface |

Cache `level` is `L1` for in-process memory only, or `L1L2` to add a distributed tier shared
across scaled-out instances. `L1L2` is the default, so a scaled-out deployment that has not
configured the distributed tier should say so deliberately rather than inherit it.

## The other endpoints on the same host

Besides `/api` and `/graphql`, a running instance serves an OpenAPI document and a health
endpoint, and at 2.0 the OpenAPI document is permission aware: `/openapi/{role}` renders only what
that role can call, and is available in development mode only so that roles cannot be enumerated
in production. The protocol endpoint for agents is on by default at `/mcp` over the same entities
and permissions; it is covered by `dab-mcp-endpoint`, not here.
